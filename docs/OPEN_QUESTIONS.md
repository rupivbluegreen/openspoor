## Architecture and operations

| Area | Question | Where |
|---|---|---|
| Workflows | Temporal is in the compose stack (ADR-004), but long-running human workflows (recall, batch release) and connector retries run on the PostgreSQL job queue. Wire Temporal workers when a workflow needs durable timers measured in weeks. | ADR-004, internal/act/workflows.go |
| SFTP | Inbound EDI files are parsed with `pkg/edi`, which reads X12 850, the X12 sets with a segment template and the EDIFACT messages of the type registry (see the B2B transaction types row); other transaction sets fail with an alert. Outbound drops are EPCIS files, and B2B documents (X12 or EDIFACT, rendered with `pkg/edi`) for a partner bound to the instance (`partnerId`, `documentDir`, `documentFormat`); the file naming, folder layout and whether a partner expects one document per file or batches are our defaults, not a partner requirement, and no acknowledgement (997/CONTRL) is expected back over SFTP. Delivery is confirmed by the upload; partner pickup is not observable over SFTP. | internal/connectors/sftp.go |
| AS2 profile | AS2 (RFC 4130) runs in process (ADR-007) with a default profile: SHA-256 signatures over RSA keys (at least 2048 bits), AES-256-CBC content encryption with RSA key transport, signed MDN receipts (sync and async), AS2-Version 1.0, with per-partner options (below). No document we hold says which profile DSCSA trading partners require. Per-partner digest, cipher and compression options now exist (see the AS2 digest and cipher options row). Open: 3DES and RC2, AES-GCM, RSA-OAEP, ECC keys, AS2 1.2 filename preservation, whether signing, encryption and signed receipts are mandatory (a new connection defaults to all three), and the payload media type and document shape for a TI/TS over AS2 (we send the EPCIS 2.0 JSON-LD document as `application/ld+json`). | pkg/as2, internal/partners/as2.go, internal/dscsa/as2.go |
| AS2 trust | Partner certificates are pinned (the signer must be byte-identical to the certificate exchanged at onboarding, or to the partner's registered next certificate during a rotation); there is no chain building, trust anchor list or CRL/OCSP revocation check. Expiry alerts (60, 30, 7 days and on expiry) and the current/next rotation flow exist (see the AS2 certificate lifecycle row). | pkg/as2/parse.go |
| AS2 certificate lifecycle | The expiry thresholds (60, 30, 7 days and on expiry) are the requested working values, not a requirement of a trading-partner agreement. Open: after the switch date the previous certificate is dropped when the job promotes the next one (no configurable grace period for a partner that still signs with, or encrypts to, the old certificate); how partners announce and exchange a next certificate (we only hold what an administrator enters, there is no in-band exchange); whether the next certificate must differ in subject or key from the current one (only the certificate itself must differ); the schedule runs every 30 minutes, so promotion can lag the chosen date by that long (signing and encryption already follow the date at use); a stored `not_after` is what the alerts use, the certificate itself is what is checked when sending. | internal/dscsa/as2_certs.go, internal/partners/as2_certs.go, pkg/as2/certinfo.go |
| AS2 digest and cipher options | Per-partner choices are SHA-256 (default), SHA-384, SHA-512 and AES-256-CBC (default) or AES-128-CBC; SHA-1 only for a partner flagged `legacy`. They follow secondary descriptions of public AS2 practice, not a partner specification. Open: which of these DSCSA trading partners actually accept; whether AES-GCM, 3DES, RSA-OAEP or ECC keys are needed (refused today); the micalg spelling for SHA-1 (we send `sha1` and read both `sha1` and `sha-1`); the rule that inbound signatures and ciphers must be at least as strong as the partner's configured choice (a legacy partner accepts any digest) is ours; the digest asked for in `signed-receipt-micalg` follows the message digest and an unsigned message with an unsupported or too weak request is answered with SHA-256 (the sender then sees a MIC mismatch). | pkg/as2/alg.go, pkg/as2/parse.go |
| AS2 legacy flag | `legacy` admits SHA-1 for one partner (signatures, receipts and, if chosen, outbound messages). It is an explicit, audited setting with an open alert and an overview warning, and the database refuses SHA-1 without it. Open: whether such partners must be supported at all for DSCSA, whether the flag should expire or need a recorded reason or approval, and whether the cipher side needs a legacy exception (3DES is not offered). | internal/partners/as2.go |
| AS2 compression | Optional compression is RFC 5402 style (CMS CompressedData, zlib) applied to the MIME entity before signing and encryption; the integrity check covers the compressed entity because that is the signed first part. Described from secondary sources: the order of compress, sign and encrypt, the integrity-check coverage and which partners expect compression are unverified. A compressed message must be signed or encrypted (the integrity check of a bare compressed entity is not defined here), and decompression is bounded to the message size limit. Compressed data is read as DER only (BER from other implementations may be refused). | pkg/as2/compress.go |
| AS2 receipt options | The receipt signature digest is chosen per partner and the receipt's integrity-check digest follows the message; the MDN mode is sync or async per partner. Whether partners require a particular receipt digest, and whether unsigned receipts are ever acceptable, is unverified (we always request and require signed receipts). | internal/dscsa/as2.go |
| AS2 unsigned integrity check | RFC 4130 does not pin down which header lines the message integrity check covers for a message that is neither signed nor encrypted; both ends of Open Spoor use Content-Type, Content-Transfer-Encoding and Content-Disposition. Signed messages (the default) follow the RFC (MIC over the signed first part). | pkg/as2/mime.go |
| AS2 inbound ASN | An inbound TI/TS over AS2 carries no ASN, so the reconciliation against the ASN (supplied by the caller on the HTTPS path) is empty and the shipment is stored as received. The purchase order number is read from the TI/TS header or its purchase-order business transaction. Where partners send the despatch advice is not specified. | internal/dscsa/as2.go |
| AS2 connection test | AS2 defines no test or ping message, so the onboarding connection test for the AS2 channel fails with an explanation; a connection is verified by a first shipment (the signed receipt is the proof). | internal/link/onboarding.go |
| AS2 endpoint abuse | `POST /api/v1/as2/receive` is public. Unknown senders get 403 before any cryptography, but a connected partner's identifier (not a secret) lets anyone make the node do a decryption and signature check, and each failed message adds a message-log row (one alert per sender and reason). There is no per-sender rate limit or row cap yet. Async receipts are only delivered to the URL configured for the connection, never to a URL named in the message. | internal/dscsa/as2.go |
| Federation | The Verifiable Credential binding organisations to nodes is not built (license credentials are, see ADR-010); `did:key` is not supported yet. | ADR-008 |
| GDPR vs GxP | Decided: audit entries are pseudonymised when written, so erasure and retention do not conflict. | Archive | Captures older than `OPENSPOOR_ARCHIVE_AFTER_DAYS` are copied to S3 as gzipped EPCIS 2.0 files; events also stay in PostgreSQL. Moving cold events out of PostgreSQL (the larger-tier plan) is not built: decide when retention or volume calls for it. | internal/epcis/archive.go |

| Document reading | OCR is not built: scanned documents (a PDF without a text layer, images) are refused. | Agent evaluation | The golden datasets are small and synthetic; a score says an agent behaves as the dataset expects, not how accurate it is on real data. ## Security gaps (from the ASVS self-assessment, `docs/security/asvs-l2.md`)

| Area | Question | Where |
|---|---|---|
| Authentication | Local accounts have a TOTP second factor (optional per user; a tenant can require it for administrators) but no phishing-resistant factor (WebAuthn), none required for other roles, and e-signatures re-authenticate with the password alone. TODO(spec): whether a TOTP code counts as a second signature component for 21 CFR Part 11 e-signatures is not asserted; confirm against the requirement before relying on it. Recovery codes carry about 60 bits (ASVS 2.6.2 asks 112 bits or per-code salts). No breached-password (k-anonymity) check beyond the embedded deny-list; password limits are 10 to 72 bytes. | internal/platform, internal/core/auth |
| Credential recovery | The recovery token lifetime (30 minutes), the throttle (3 requests per account and window, then back-off), the number of recovery codes (10) and the notification e-mails are engineering defaults, not requirements: decide whether they should be settings. Recovery needs an SMTP relay; without one the endpoint answers but sends nothing. Identity proofing for an administrator's lost second factor is left to the organisation (another administrator resets it). | internal/platform/account.go |
| Sessions | Revocation is per user (a sign-out ends all of the user's sessions), not per device, and costs one database read per request. There is no idle timeout; local tokens live `OPENSPOOR_JWT_TTL` (12 h default). OIDC tokens cannot be revoked from here. Operator support tokens are not tied to a stored session. Decide whether to add a session table (per-device sign-out, idle timeout, session list). The `openspoor_token` cookie is no longer accepted. | internal/core/auth, internal/platform |
| Cryptography | The master key is a single key under the operator's control. `openspoor rotate-keys` re-seals the tenant data keys and the node key, but needs the processes stopped and does not rotate data keys themselves; there is no built-in KMS integration. | internal/core/secrets, internal/app/rotate.go, docs/runbooks/secrets.md |
| Outbound requests | Webhooks, connectors (REST, SFTP, hub), DSCSA HTTPS, AS2 and partner probes now go through the shared egress guard (`internal/core/egress`, `OPENSPOOR_EGRESS_ALLOW_PRIVATE`, `OPENSPOOR_EGRESS_ALLOW_CIDRS`). **Still open:** federation peer delivery (`internal/link/federation.go` builds its own pinned client from `http.DefaultTransport`; use `egress.NewTransport()` there, keep the pinning `TLSClientConfig`, and `egress.CheckRedirect`) and the regulatory-source watcher (`internal/act/safefetch.go` has its own equivalent check; replace `newWatchClient`/`IsBlockedIP` by `egress.Client`/`egress.Policy`, keeping its https-only and default-port rule). | Rate limiting | Authenticated API calls are limited per tenant and per API key by plan (`internal/core/ratelimit`, `OPENSPOOR_RATE_LIMIT`, `OPENSPOOR_RATE_LIMITS`; 429 with Retry-After; operators exempt).
